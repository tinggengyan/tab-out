## 0. 产品边界（建议写进仓库，作为后续每个任务的验收前提）

**一句话定位：** 打开新标签页，按站点看清当前所有标签，并一键关闭、去重或收纳；收纳过的页面随时一键找回。

### 做

- 按站点聚合当前打开的标签。
- 每个站点支持一键关闭、一键去重、一键收纳。
- 首页可直接看到收纳记录并一键找回。
- 稍后查看（单页待读）。
- 所有破坏性操作都可撤销。

### 不做（除非负责人书面推翻）

- 不在首页放项目管理、会话快照、AI 或网页正文采集。
- 不做付费墙。
- 不做"网站别名搜索"这类启动器功能。
- 不为了新功能在首页增加常驻控件。

### 守护指标

做成 e2e 断言，以后每个任务都要跑。夹具与诊断报告一致：5 个站点、15 个标签、3 个精确重复、3 条稍后查看，1440×900，zh-CN。

| 指标 | 原版 | 当前 | 目标（P2 完成后） |
|---|---|---|---|
| 首屏常驻可见交互控件数 | 51 | 68 | ≤ 30 |
| 首张卡片顶部位置 | 80px | 190px | ≤ 100px |
| 关闭本站点击数 | 1 | 2 | 1，可撤销 |
| 本站去重点击数 | 1 | 1，不可撤销 | 1，可撤销 |
| 全局去重点击数 | 无 | 2（底栏清理） | 1（首页区头） |
| 收纳本站点击数 | 1 | 5 次、2 层弹窗 | 1，无弹窗，可撤销 |
| 首页找回一条收纳点击数 | 1 | 约 3-4 次，需切换视图 | 1 |
| 任一点击引起的其他元素位移（被关闭的卡片除外） | — | 有（"更多"内联展开） | 0 |

### 1.3 "收纳"的唯一定义与找回路径

- **定义：** 收纳 = 把一组打开的页面存成一条**收纳记录**，并关闭这些页面。
  - 来源可以是一个站点、"全部收纳"（当前窗口所有可保存的非固定页），或快捷键 Alt+Shift+C。
  - 固定页和浏览器内页不会被关闭。沿用 `project-service` 已有的保护规则。
- **存储：** 继续使用 `workspacesV2`，不新建对象类型。现有的项目、已迁移的旧收纳和新收纳记录都在同一个列表里。
  - 默认名称：站点名，或"窗口 · 时间"。用户可以改名。
- **找回：**
  - 首页右栏"已收纳"→点"恢复"（1 次）：在当前窗口补开缺失页面，已经打开的跳过。
  - 点记录标题展开单页列表，可以单页打开。
  - "查看全部收纳"进入完整列表。它就是现有的"已保存"视图简化后改名而来。
- **恢复后记录怎么办【待拍板，问题 1】：**
  - **默认假设（推荐）：** 通过"收纳"新产生的记录，恢复全部后移入回收站，toast 可撤销，与原版 OneTab 式一致。已有记录（迁移来的旧收纳和命名项目）保持"打开后保留"。
  - 实现方式：新增键 `collectRecordIdsV1`（字符串数组），只记录哪些 id 是"一次性收纳"。**不改 `workspacesV2` 的结构**，符合仓库"不原地改键结构"的规则。
  - 如果负责人选"一律保留"：不写这个键即可，其余不变。
- **术语表**（UI 只允许出现这些词）：

| 词 | 含义 |
|---|---|
| 收纳 | 动作 |
| 已收纳 / 收纳记录 | 收纳产生的对象 |
| 恢复 | 找回收纳记录 |
| 稍后查看 | 单页待读 |
| 回收站 | 删除后可恢复的地方 |
| 历史快照 | 自动或手动保存的浏览现场 |

  以下词在 UI 中**全部停用**：项目、已保存、保存分组、分组、收起、继续项目、历史现场。

### P1：收纳闭环与术语统一

**目标：** 首页右栏可以看到并一键恢复收纳记录；同一对象在 UI 中只有一个名字；原"已保存"视图简化为"全部收纳"列表。

**改动范围：**

## 4. 风险

| 风险 | 影响 | 应对 |
|---|---|---|
| 收纳恢复语义变化，导致用户以为会保留的记录消失 | 数据信任受损 | 只对新产生的一键收纳记录启用消费式（`collectRecordIdsV1`），并且进入回收站可撤销；已有记录保持保留 |
| 一键收纳跳过预览，误关页面 | 误操作 | 复用 `project-service` 的固定页和内页保护；toast 撤销；首次使用给一次轻提示（沿用 `closeAllPreviewSeenV1` 的做法） |
| 站点组跨多个窗口，park 接口按窗口预览 | 收纳不完整或失败 | P0 前做技术确认；不支持就按窗口分批，结果 toast 显示实际数量 |
| 测试与函数切片耦合，改写量大 | 工期延长 | 每阶段预留测试改写；P0 同时引入守护 e2e，用结果断言替代实现细节断言 |
| 冻结浏览记忆影响负责人自用 | 自用体验下降 | 导出始终可用；问题 2 决定后再删；如果选择拆分，先做好新扩展再撤 |
| P2b 回滚触发权限重新授权 | 用户被打扰 | manifest 删减单独提交，延后合入 |
| 需求再次把功能拉回首页 | 再次跑偏 | §0 边界写进仓库；守护 e2e 作为所有任务的硬性验收；新功能默认进设置 |
| 四种语言维护成本 | 每次改文案要写 4 份 | 本次大量删键会降低成本；新增文案保持最少 |

## 5. 需要负责人拍板的问题（最重要的在前）

1. **收纳恢复后记录是消失（OneTab 式）还是保留（项目式）？** 默认假设：新收纳消失并进回收站，已有记录保留。这个答案决定 P1 的实现，以及"全部收纳"列表是否会越积越长。
2. **浏览记忆（含 AI）最终去向：** 冻结后留在设置、拆成独立扩展，还是删除？这决定 P2 和 P3 的范围、全站点可选权限和 IndexedDB 数据的处理。
3. **首页还要不要支持"跨站点的一件事"？** 选项：保留显式"多选模式"，或者完全移除、交给 Chrome 标签组。这决定 P0 的多选入口和选择栏是否保留。
4. **本阶段是否放弃商业化？** 是否签发过任何 license？这决定授权代码是在 P3 删除还是长期隐藏，以及快照和回收站的额度是否统一放开。
5. **除你之外是否有外部安装用户？是否计划上架？** 这决定数据兼容验收要多严格、是否保留四种语言和引导页，以及 P3 是否允许删除保留不读的键。
