# Tab Out 功能筛选建议

日期：2026-11-01。依据：[Backlog](../PRODUCT_BACKLOG.md)、[实现程度基线](2026-11-01.md)、用户明确需求及本次核对的竞品官方说明。

**建议收敛为一条主线：找回未收藏的内容，并能直接继续使用。** 下一轮优先候选为 BL-011，BL-003复用现有能力补上后续操作；BL-001／BL-010负责数据与质量保障。此处是具体产品建议，尚未作为用户确认的开发范围，也不启动实现。

用户澄清要一起审视和筛选，非定时任务；误建的自动化已删除。

## 为什么选择这条主线

| 方向 | 已有基础与需求 | 增量价值判断 | 本轮建议 |
| --- | --- | --- | --- |
| 标签清理与临时收纳 | 当前已有分组、去重、收纳、撤销与保存恢复 | 容易说明用途，增量可小；但基础整理能力竞争充分 | 保留和打磨，不继续堆多个独立整理入口 |
| 完整项目工作台 | 2.2.0 已有手动选页、保存、恢复与安全切换 | 对有稳定项目分类习惯的人有用；当前还缺实际试用证据来证明应继续加复杂度 | 先使用现有版本，不预先扩大项目管理体系 |
| 浏览内容找回与继续使用 | 用户直接提出“过去30天看过但没收藏”的需求，明确公开、登录后与内网都需要 | 能处理事后才发现有用的内容；开发代价大，但值得通过技术验证决定是否加大投入 | 作为下一阶段主线候选 |

选择依据是需求具体、与现有标签生命周期相接，以及可通过找回测试验证；不是因为加上 AI 就能形成优势。

## 差异化需要实际兑现什么

Chrome 已有自然语言历史搜索；其帮助页说明现阶段的地域／语言条件、启用后的正文记录方式，以及只展示少量最佳匹配。Gemini 也有历史搜索，要求个人 Google 账户和历史同步，当前不适用于工作或学校账户。[Chrome 官方说明](https://support.google.com/chrome/answer/15305774?hl=en)、[Gemini 官方说明](https://support.google.com/chrome/answer/16716225?hl=en)。这些是本次可访问文档的条件，后续可能变化。

因此，以下是需要验证的执行优势，而非已经成立的独占能力：

1. **不靠记住标题。** 用中文、观点或案例描述，也能找回正文相关的页面；需与普通标题／网址搜索对照。
2. **覆盖真实工作浏览。** 公开、登录后和内网页面一起验证，不按题材或域名限定候选范围。前提是用户有权限且浏览器允许扩展访问；不限域名不是承诺所有页面都能提取正文。
3. **找得到也能核对。** 展示原链接、访问时间、当时记录或当前获取的内容版本、命中段落；覆盖不足可见，摘要与原文对应。
4. **找回后立即继续。** 单页跳转、批量打开、跳过已打开页面，按需暂存到已有集合；复用当前能力，减少重新整理。
5. **内容边界清楚。** 本机保存与外部模型处理分别定义，明确记录、暂停、清除、正文保留与外发范围。仅声称“本地”不足以成为差异，必须通过效果、成本与控制体验验证。

可积累的长期优势是页面提取覆盖、中文找回评测、相关性反馈和完整使用流程。个人内容应可导出，不用数据锁定替代产品价值。

## 建议开发组合及最小范围

### 主功能：BL-011 AI 浏览记忆搜索

首个可验证版本应形成完整链路：

- 授权后导入仍存在的历史元数据，提供最近30天等查询条件；清楚区分只保留网址／标题的旧记录和已经取得正文的记录。
- 用户主动启用后，在日常浏览时提取允许访问页面的已加载正文，并持续建立本机索引；公开与登录后内容采用通用路径，失败可见。
- 同时使用关键词和按内容意思检索，呈现带原链接、访问时间、内容片段的结果。仅增加历史列表或标题搜索不算达到这个目标。
- 支持暂停、删除、排除与容量控制；保留期限、模型执行方式需在技术方案中明确。
- 先证明能找准，再加入可选的简短总结；总结必须来自实际取得的正文并能定位来源。

最大的未知是通用正文提取的覆盖、设备上的语义检索效果与性能，以及历史内容尚未积累时的首用价值。目前尚不能给出可靠工期或保证30天内所有旧页面都可按正文搜索。

### 配套体验：BL-003 找回后继续使用

- 第一阶段复用既有标签跳转、只补缺失和集合保存，增加搜索结果中的对应操作，不重写恢复服务。
- 最后停留页面、关键页面和可选一句备注属于后续增强，不能先要求用户留下笔记才能找回内容。
- BL-002 的默认时间名称可作为保存入口的小改进；BL-008 可并入结果的可选 Markdown 导出，二者都不单立新主线。

### 发布保障：BL-001 与 BL-010

- 先明确旧标签资产和新增正文／索引分别如何备份、恢复与清除；现有自身配置导出不能默认覆盖未来的新存储。
- 用独立文件恢复、容量压力、部分写入／索引失败和重启场景，验证实际承诺的数据范围。
- 浏览记录、正文和摘要应能追溯来源；不把抓到的网址数当成可全文搜索的文章数。
- 按明确支持的规模测响应、容量和恢复结果。这些工作支撑产品可信度，不单独作为获客卖点。

## 对全部 Backlog 的取舍

| 条目 | 本轮建议 | 原因 |
| --- | --- | --- |
| BL-011 | 作为下一轮主线候选，先做可运行的技术验证 | 需求来自核心用户，任务明确；复杂度高，先验证关键未知 |
| BL-003 | 作为主线的后续操作层，复用现有能力 | 从找到网页到继续工作，能利用当前投入 |
| BL-001／BL-010 | 纳入发布与数据质量工作 | 长期积累的内容需要对应的恢复和容量保证 |
| BL-002 | 合并改进现有保存入口 | 改动较小，但单独不足以形成独特优势 |
| BL-008 | 合并为可选结果导出 | 普通导出已有竞品提供，不值得单独建设另一套 AI 产品 |
| BL-004 | 暂缓，明确迁移用户后再做 | 新主线可从浏览记录开始，不依赖先迁移其他工具的收藏；仍保留未来增长价值 |
| BL-005 | 暂缓，待内容相关性验证后评估复用 | 现在另做自动分组会同时引入另一套推断与纠错问题 |
| BL-006 | 暂缓，观察实际入口阻力 | 当前已有快捷键、地址栏和工作台，可先验证找回价值 |
| BL-007 | 暂缓 | 同步、密钥和冲突处理投入大，会分散首个找回版本的验证 |
| BL-009 | 观察，暂不调整额度或定价 | 功能是否产生持续价值和付费意愿仍未知 |

## 进入正式开发前的技术验证

推荐用小型可运行验证收敛不确定性，保持全部题材与域名的产品范围：

1. 准备覆盖公开文章、登录后文档和内网的测试内容；仅使用明确允许用于验证的样本，记录各页面正文能否取得及失败原因。
2. 建议先建立20个带目标页面的自然语言找回问题，包含标题未出现的正文线索；对照原有关键词搜索。样本数是内部试验建议，不代表统计显著或行业标准。
3. 可以将“至少16个问题的目标页进入前5个结果”作为第一轮调整用门槛；这是待讨论目标，尚无实测结果。另行测量延迟、资源开销、中文表现和内容类型覆盖，不能以单一命中数判断全部可用性。
4. 所有结果必须对应真实记录，提取失败与无正文状态应如实呈现；生成总结时核对每条结论的原文依据。
5. 找回效果达标且成本可接受，再冻结正式需求、技术方案与阶段范围。效果不达标时，应先定位提取、检索或查询理解的问题，不用先加更多界面功能掩盖。

## 当前决定与未决定

- **已确认：** 取消误建自动化；开展当前产品筛选；BL-011 覆盖公开／登录后／内网，不限题材和域名。
- **本轮建议：** 采用“找回未收藏内容，并直接继续使用”的主线与上述开发组合。
- **尚未决定：** 用户是否采用这条主线；模型运行和内容保留方案；验证样本及正式验收门槛；开发排期。
- **本次验证：** 核对现有模块和竞品官方页面，更新筛选文档；没有执行产品改动或新的搜索原型评测。
